# 2026-10-09

## 统一时区方案落地（v3 定稿）

**背景**：日志时间戳显示 UTC（`2026-10-09T05:14:01.517800Z`）而非本地时区，排查后发现是全项目性问题，不止日志。

**设计原则（用户拍板）**：框架只提供"解析链 + 出口"，**不持有默认时区**。时区配置归业务层，
但入口落在框架 config（`[time].timezone`），非必填。

**解析链**：`[time].timezone`（已配置且合法 → 采用；非法 → 启动期 fail-fast）
→ 系统时区（`TZ` 环境变量 → OS 本地偏移）→ UTC（兜底）。

**改动清单**：
- `Cargo.toml`：`chrono-tz` 从 optional 提为**常驻依赖**（原只在 `scheduler`/`i18n` feature 下，
  但日志出口需在默认构建可用）；两 feature 中的重复声明已清理。
- `src/config/sections/time.rs`（新）：`TimeSettings { timezone: Option<String> }`，
  `timezone_name()` 归一化（空白串 = 未配置）。
- `src/config/settings.rs`：`Settings` 聚合 `pub time: TimeSettings`。
- `src/utils/time.rs`：新增解析内核 `resolve_display_tz`（全项目唯一时区解析入口）、
  `system_tz`（`OnceLock` 缓存 + `catch_unwind` 防 `chrono::Local` panic + 常见时区候选匹配）、
  展示出口 `display_rfc3339` / `format_display` / `now_display_rfc3339`。
  瞬时点出口（`now_ms`/`now_secs`/`now_utc`/`rfc3339`）**保持 UTC 不变**。
- `src/observability/logging.rs`：新增 `TzTimer`（实现 `FormatTime`），两个 fmt layer
  （console/json）各挂载；非法时区启动期 `panic` fail-fast。
- `src/task/cron.rs`：`resolve_job_tz` 走解析链，**修复文档 04:416 点名的"时区解析失败静默回落 UTC"缺陷**
  （改为 fail-fast）；`with_timezone` 重构为 `resolve_job_tz` + `build_job`。
- `src/config/sections/i18n.rs`：`default_timezone` 缺省值从 `"UTC"` 改为空串（未配置语义）。
- `src/i18n/format.rs`：新增 `format_datetime_default`（走解析链）。
- 文档：`docs/03` 新增第十一节·2「时区」、i18n 与 cron 章节同步；`docs/02` 新增 20.1 节；
  `docs/04` 勾销 cron 时区缺陷；`README.md` feature 表加 `time` 行；示例配置加 `[time]`。

**端到端验证**（临时工程实测）：配 `Asia/Shanghai` → 日志输出
`2026-10-09T13:58:04.505+08:00`；配 `Asia/Shanghi`（拼错）→ 启动 panic 且报错信息可操作。
测试：77 个全绿（47 lib + 5 + 22 core_test + 3）。

**硬约束（勿改）**：DB 审计字段入库、雪花 ID、JWT iat/exp、CSRF exp、各类 TTL 相对时长、
`Instant` 单调时钟 —— 全部必须保持 UTC。API JSON 里 `DateTime<Utc>` 默认仍序列化为 `...Z`。

**遗留**：日志 timer 在 init 时构造，改时区需重启（已写入文档）；
`fixed_offset_to_tz` 走固定偏移时无法处理 DST（已写入文档，建议显式配 `TZ` 或 `[time].timezone`）。
