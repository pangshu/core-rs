## 调研：migration feature 是否该留在公共框架（2026-10-06）

**主流 Rust 框架分两派**：
- 全栈型（内置迁移）：**Loco**（SeaORM 基础，`auto_migrate` 配置开关，官方建议 dev 开、生产关）、**Rwf**（migrations 目录自动执行）。
- 组合型（不含迁移）：**axum / actix-web**（无 DB 层）、**rocket**（`rocket_db_pools` 官方文档明示只做连接池，用迁移需自行加 sqlx 的 `migrate` feature）、**poem / salvo / warp / tide**。
- ORM 层普遍支持"启动时执行"：SeaORM《Running Migration》原文 "apply or revert migrations in the terminal **or on application startup**"（`Migrator::up(db, None)`）；SQLx `migrate!()`、Diesel `embed_migrations!`、Refinery 同理。

**对 core-rs 的判断**：迁移"执行器"无业务词 → 符合 lib.rs 的准入判据，进框架自洽；且形态最保守（只做钩子+泛型帮手，连 CLI 都没做），feature 可关、调用点 opt-in。

**发现的真实设计缺口（待决策）**：core-rs 只要调用 `.migrations()` 就无条件在 `serve()` 启动时跑迁移，**没有配置门控**；Loco 用 `auto_migrate` 开关保护（生产建议关闭，避免多实例滚动发布时并发 DDL 竞态）。建议给 core-rs 加 `[database] auto_migrate` 类开关，默认关或仅 development 为 true。

### 补充（同日修正对比集）：用户要的是 Spring Boot 那一档，不是 axum 那一档

**Spring Boot 自身的答案（最关键）**：Spring Boot **不自己实现迁移**，它集成第三方 **Flyway / Liquibase**，但把迁移**接进启动生命周期并默认自动执行**——`spring.flyway.enabled` 默认 `true`，连接池建立后、开始服务前自动运行。**core-rs 的 `.migrations(Migrator)` → `serve()` 第 1 步，本质是同一模式的翻版，且比 Spring Boot 更保守（需显式调用才跑）。**

**Rust「全家桶」框架横向对比**：
| 框架 | 定位 | 迁移 |
|---|---|---|
| **Loco** | Rails/Spring Boot 风格，最接近 | ✅ 内置（SeaORM）+ `auto_migrate` 开关，dev 开/生产关 |
| **summer-rs**（原 spring-rs） | 明确 "inspired by Java's SpringBoot"，插件≈starter | ❌ **官方插件集不含迁移**；仅第三方 `summer-sqlx-migration-plugin` |
| **Rwf** | 全栈 | ✅ 内置，但只走 **CLI**（`rwf-cli migrate run`），非启动时自动 |
| **Zino** | spec-driven 强观点框架 | ⚠️ 只有 **auto-DDL**（`create_table()` / `synchronize_schema()`），属 Hibernate `ddl-auto` 路线，**不是版本化迁移** |

**跨语言参照**：Rails / Django / Laravel / Spring Boot(+Flyway) / NestJS(+TypeORM) 等全家桶**几乎都内置迁移**。Rust 是例外，因为 Rust 的全家桶生态本身还很年轻。

**结论**：core-rs 内置迁移符合"应用框架"这一档的主流做法，且与 Spring Boot 的实现路径一致；改进点仍在"要不要无条件自动跑"（建议加配置门控）。
