## 框架能力缺口分析（对标 GoFrame，未改代码）

**背景**：用户提问「本项目是为团队开发各种应用而做的框架，有点像 golang 的 gf，现在还缺什么」。

**调研**：通读 README、Cargo.toml、docs/02 设计文档、docs/03 使用指南目录、docs/04 代码审查报告、lib.rs/prelude.rs、src 文件清单、examples/demo 结构；grep 确认无 CLI/代码生成/对象存储/操作审计/出站 HTTP 客户端/multipart。

**核心结论**：core-rs 目前是「运行时库」，gf 是「运行时 + 工具链 + 代码生成 + 全家桶基础库 + 文档生态」。运行时能力（接入层、数据/消息层）已达 gf 的六七成，但工程/生态层基本空白。

**六类缺口（按对团队价值排序）**：
1. 工具链与代码生成（最大结构性缺口）：无 CLI/脚手架/项目模板；无按 DB schema 生成 entity/DAO/Service/Controller（gf `gen dao/service/ctrl` 是团队提效核心）；迁移只能手写。
2. 出站集成层：无统一 HTTP 客户端封装（对标 gclient：超时/重试/熔断/trace 注入/日志）；resilience 模块存在但无真实调用点（审查 P1-57 指出 bulkhead 是死代码）。
3. 文件与数据治理：storage/ 仅预留未落地（S3、multipart 上传、分片续传、转码回调）；无操作审计日志；无数据脱敏/透明字段加密；无接口签名防重放。
4. 数据访问范式：只有 Crud trait，实体/Repo 全手写，无 model/dao/service 分层与生成；无 DTO↔Entity↔VO 映射辅助；无多数据源/读写分离/分库分表；无关系预加载封装。
5. 可靠性与正确性债务（更紧急的一轴）：docs/04 记 13 个 P0，多为「接口齐、实现没对齐、静默失效」（authz 授权绕过、ip_filter fail-open、幂等跨用户重放、Redis 队列不可用、热更新订阅失效、密钥进日志等）。团队框架底线是可信 —— 「有 authz 但形同虚设」比「没有 authz」更危险。安全关键路径测试零覆盖。
6. 交付与协作：无 Dockerfile/K8s/Helm 模板、CI 模板、版本发布策略（仍 path 依赖）；无特性开关；OpenAPI 明确不进（团队协作痛点，建议重估为可选导出）；缺编码规范/ADR/贡献指南。

**附带（来自 10-07 日志）**：中间件「组合权留应用」文档承诺与「全量全局写死装配」实现不符，已另有 docs/05 方案。

## 答疑：出站 HTTP 客户端 vs axum（未改代码）

用户问「出站客户端不是直接用框架里的 axum 吗」。结论：axum 是**服务端**框架（hyper::server，监听/接单/路由分发），出站客户端是**调用方**（hyper::client/reqwest，主动建连/发请求/解析响应），二者方向相反、不可互换。共享的只是 HTTP 协议 + hyper/tower 底层。

**框架现状（事实）**：reqwest 已是 optional 依赖，但仅两处裸用 —— `config/source.rs:104`（远端配置拉取，有 timeout）、`auth/oauth2.rs:95/105`（每次 `reqwest::Client::new()` 新建、无 timeout/重试/熔断/trace）。`resilience::Registry::call(dep, f)` 已提供「重试+熔断」组合，但无任何出站调用点（P1-57）。因此缺的不是「能否发 HTTP」，而是**统一封装层**：包 reqwest + 接 Registry + 注入 traceparent + 出站结构化日志 + 连接池/超时配置化。

**技术要点**：reqwest 不是 tower::Service，套不上 tower 层；若想复用 tower 的 timeout/retry/trace，需改用 hyper client 自建。resilience 是自研（非 tower layer），需适配。

## 答疑：四个框架谁有 migration（未改代码）

**问题**：上面比较过的框架（core-rs / GoFrame / go-admin-core / go-gin-api）谁有 migration 功能。

**结论：只有 core-rs 有。** 逐项核实：
- **core-rs**：✅ `migration` feature（默认开启）。`src/db/migrator.rs` 封装 sea-orm-migration，提供 `up/down/fresh/status` 四个泛型函数；`App::migrations(Migrator)` 启动自动执行；手动走 `src/bin/migrate.rs`（框架无法提供统一 CLI，因 Migrator 类型定义在使用方）。
- **GoFrame (gf)**：❌ 明确不做。阿里云文章《为什么GoFrame不支持migrate功能》记录作者原话「goframe 不支持，并且**以后也不会支持**」，理由：migrate 不够严谨，没有强规范约束成员易出大问题，企业级/TOB「稳定第一」。官方文档 gdb 只有「ORM模型生成 gf gen dao/model」，无迁移章节；官方另发文章推荐第三方 golang-migrate。
- **go-admin-core**：❌ 无。v2.11 顶层目录 = api/captcha/casbin/config/docs/errors/jwtauth/logger/observe/response/scripts/sdk/server/storage/tools。已核实 `storage/`（仅 cache/queue/redis + legacy）与 `sdk/`（api/bootstrap/config/contract/pkg/runtime/service）**均无迁移包**。
- **go-gin-api**：❌ 无。README 18 项集成组件无迁移；`scripts/` 仅 gormgen / gqlgen / handlergen / swagger 四个生成脚本。

**重要澄清**：go-admin（**脚手架**，非 core）有迁移 —— `go-admin migrate` 命令 + `cmd/migrate/migration/version/`（毫秒时间戳版本号）+ `sys_migration` 表。所以 go-admin 生态整体是有迁移的，只是在脚手架层。

**对 core-rs 的启示**：core-rs 走的是「版本化迁移」路线（sea-orm-migration 装配），与 go-admin 同类；gf 的「不做」是主动设计取舍而非遗漏。

## 答疑：启动迁移是否每次都执行（未改代码）

**问题**：`.migrations(Migrator).serve()` 是不是每次启动都做一次迁移。

**结论：每次启动都会「调用」迁移，但只有未应用的才会真正执行 DDL。** 读 `sea-orm-migration 2.0.4` 源码（`~/.cargo/registry/src/index.crates.io-*/sea-orm-migration-2.0.4/src/`）确认流程：
1. `migrator.rs:235` `up()` → `exec_up()` → `M::install(db)`：`CREATE TABLE IF NOT EXISTS seaql_migrations`（`exec.rs:88-100`，`if_not_exists()`）。
2. `M::get_pending_migrations(db)`：`exec.rs:16-34` SELECT version ORDER BY version ASC；`exec.rs:52-86` 用 HashSet 求差集（代码里的迁移 − 已应用）= pending。**若 DB 有 version 但代码缺文件 → 直接 Err**（防代码回滚/文件误删）。
3. `exec_up_with`（`exec.rs:242-286`）：pending 为空则只打 `No pending migrations` 日志、不执行任何 DDL；否则逐个 `migration.up()` + `insert_migration_record()`。

**关键事实（长期有效）**：
- 幂等键 = `MigrationTrait::name()`（如 `m20260101_000001_create_users`），改文件名/结构体名 = 删旧版本 + 加新版本。
- `seaql_migrations.version` 是**主键**（`seaql_migrations.rs:7`）→ 多副本并发启动会主键冲突，sea-orm **无锁保护**。
- `should_use_transaction`（`exec.rs:200-205`）：默认**只有 Postgres 开事务**；MySQL/SQLite 默认不开 → demo 用 sqlite，迁移中途失败会留半成品表结构。可在迁移里重写 `use_transaction()` 返回 `Some(true)`。
- 框架 `src/db/migrator.rs:18` 的 `migrations applied` 日志是**无条件打印**的，即使一条都没应用。
- 空转成本 = 1 条 `CREATE TABLE IF NOT EXISTS` + 1 条 SELECT + 一条 info 日志。

**建议**：开发/单机用启动自动迁移；生产多副本改为部署流程单独跑 `migrate` bin。

**产出**：对话内答疑 + 幂等判定流程图（inline SVG），未新建文件。

## 讨论：迁移放在框架内是否导致「数据库前缀无法统一」（未改代码）

**用户观点**：去掉迁移，因为放在框架内会导致数据库前缀无法统一。

**核实结论（校准因果）**：
- 框架 `src/` 里**没有任何数据库表前缀机制**；grep `prefix` 命中全是 Redis key 前缀（cache/lock/queue/session 的 `core-rs:*:`）与 `ip_filter` 的 CIDR 前缀长度。
- 框架唯一「拥有」的表名 = `seaql_migrations`（sea-orm-migration 记账表，`serve()` 步骤 1 触发 `CREATE TABLE IF NOT EXISTS`）。
- **该表名应用可重写**：`MigratorTrait::migration_table_name()` 是 trait 默认方法（migrator.rs:59-61），应用 impl 时可覆盖；`App::migrations<M>()` 接受任意 M → 应用能把迁移表改成带前缀的名字。**框架并未阻止前缀统一。**
- 真正的坑：**迁移记录表未按应用隔离**。多应用共用一库时共用 `seaql_migrations`；sea-orm 的 `get_migration_with_status`（exec.rs:74-85）在「DB 有版本但代码缺文件」时直接 `Err` → **第二个应用启动失败**。
- **文档缺口**：框架文档从未提到可以重写 `migration_table_name()`。

**两条路**：① 去掉框架迁移入口（迁移完全归应用侧自管，符合「框架不含业务约定」原则，代价是失去启动自动迁移）；② 保留但暴露迁移表名配置 / 支持多流。

**状态**：已向用户确认「前缀」具体含义与处理方式，**尚未改代码**。

**评审答疑（已补入 docs/07 第九节）**：
- Q1「合并了为什么还有两套代码」：合并的是**框架的两个入口**，不是**路由的两种分类**；分类是业务事实，只是表达者从「框架 API 形状」变为「业务 `.layer()`」。粒度由业务定（按整树 / 按子树 nest / 按单条路由），三种都只需一个 `mount`。**不可兼得**：框架不分类 ⟺ 业务必须写分类代码；要免写就得保留 `require_auth_by_default`。

## 执行：Casbin 策略表名支持运行时前缀（已完成，方案 A）

**用户诉求**：`#[sea_orm(table_name = "casbin_rule")]` 写死表名，导致无法加表前缀；要求前缀从配置文件进入、按业务切换，且不改业务代码。

**根因（长期有效）**：SeaORM 的 `table_name` 是 derive 宏**编译期**产物（生成 `Entity::TABLE: &str` 常量），`Entity::find()/insert/delete_many` 全部引用它，**运行时无任何覆盖钩子** → 纯配置改不动表名。`Column::*` 是干净的（列名与表名无关），只有表引用是问题。

**实现（框架层改动，业务零改动）**：
- `src/config/sections/authz.rs`：`AuthzSettings` 新增 `table_prefix: String`（`#[serde(default)]`，默认空）。
- `src/authz/adapter.rs`：`DbAdapter` 新增 `pub table: String`，`from_settings` 的 `db` 分支按 `format!("{}casbin_rule", settings.table_prefix)` 装配；**全部 CRUD 从 `Entity::*` 改为 sea-query 运行时拼表名**（`load/save/clear/add_policy/add_policies/remove_policy/remove_policies/remove_filtered_policy`）。实体 `Model`/`Column` 保留（仅作列标识），doc 注明实际表名走 `DbAdapter::table`。
- 新增私有助手：`table_ref(&str)`（`TableRef::Table(TableName(None, s.to_string().into()), None)`）、`row_values(ptype, rule) -> Vec<Expr>`、`nullable_eq(col, Option<String>)`。
- 文档同步：`src/authz/mod.rs`、`docs/02`、`docs/03`（`[authz]` 示例加 `table_prefix`）。

**关键 API 事实（sea-orm 2.0.4 / sea-query 1.0.2，长期有用）**：
- 用 sea-query 构造器**不需要**手动 `Statement::from_sql_and_values`：`ConnectionTrait` 有泛型 `execute<S: StatementBuilder>(&self, &S)` / `query_all<S: StatementBuilder>(&self, &S)`，可直接传 `SelectStatement/InsertStatement/DeleteStatement`（内部按 backend 生成正确占位符，Postgres 也 OK）。**手写 `?` 占位符会在 PG 上错。**
- `SimpleExpr` 在 sea-query 1.0 已是 `pub type SimpleExpr = Expr` 别名；`Expr` 是统一表达式类型。
- `ExprTrait`（`.eq()` / `.is_null()`）需 `use sea_orm::sea_query::ExprTrait`；`Expr::val(v)` 显式包值可避开与 `PartialEq::eq` 的解析歧义。
- **NULL 语义**：SeaORM `ColumnTrait::eq` 对 `None` 会生成 `IS NULL`（源码 `entity/column.rs`：`if v == v.as_null() { is_null() }`），故改写时 `nullable_eq` 必须对 None 走 `is_null()`，不能用 `= NULL`。
- `ExecResult.rows_affected` 在 sea-orm 2 是**方法**（`rows_affected()`），不是字段。
- 批量插入：`Query::insert().into_table(t).columns([...]).values_from_panic(Vec<Vec<Expr>>)`（`values_panic` 只写一行）。
- `QueryResult::try_get_by_index::<T>(idx)` 按 SELECT 列序取值（此处 id=0, ptype=1, v0..v5=2..7）。

**验证**：`cargo check` 默认 ✅ / `--features casbin` ✅（零告警）；临时测试确认 `TableRef(TableName(None, "biz_casbin_rule"))` 在 MySQL/PG/SQLite 分别渲染为 `` `biz_casbin_rule` `` / `"biz_casbin_rule"`（已删临时测试）。**注意：本机首次 `cargo test` 编译约 1 分钟，`CARGO_TARGET_DIR=D:\packages\cargo-target`。**

**遗留**：应用侧建表迁移需用同一前缀命名物理表（框架不代管迁移，见上文「移除 migration」）；`#[sea_orm(table_name = "casbin_rule")]` 仍保留为参考名，若应用误用 `Entity::find()` 会查到无前缀表（doc 已警示）。

**追问：能不能直接删掉 `#[sea_orm(table_name = "casbin_rule")]`？→ 不能，实测编译失败。**

实测（临时删除该属性后 `cargo check --features casbin`）报 `error[E0425]: cannot find type Entity in this scope`，来源是 `DeriveEntityModel` 展开。查 `sea-orm-macros 2.0.4/src/derives/entity_model.rs` 证实：`table_name` 初值 `None`（L65），仅在解析到 `#[sea_orm(table_name = ...)]` 时设置（L110-111）；`let entity_def = table_name.as_ref().map(...).unwrap_or_default()`（L129-159）——**没配就完全不生成 `Entity` 结构体**，也没有 snake_case 兜底（网上流传的「默认用结构体名 snake_case」在 2.0 不成立）。故 `table_name` 是 **`DeriveEntityModel` 的必需属性**，不是可选参考信息。

**已做的收敛改进（消除「硬编码漂移」）**：
- `src/authz/adapter.rs` 新增 `pub const CASBIN_TABLE_BASE: &str = "casbin_rule";` 与 `pub fn casbin_table_name(prefix: &str) -> String`；`from_settings` 改用 `casbin_table_name(&settings.table_prefix)`。
- 属性值仍须字面量（宏只接受 `LitStr`，无法引用常量），故保留 `"casbin_rule"` 字面量并在 doc 注明「值须等于 `CASBIN_TABLE_BASE`」。
- `src/authz/mod.rs` 增加 re-export：`pub use adapter::{casbin_table_name, CASBIN_TABLE_BASE};`，供应用侧建表迁移复用同一命名规则。
- `docs/03` 补一句迁移侧用法提示。
- 验证：`cargo check --features casbin` + `cargo clippy --features casbin --lib` 均零告警。
